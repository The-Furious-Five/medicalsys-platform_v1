## 1. Objetivo

Describir, paso a paso y con los comandos exactos, cómo se escanea la plataforma MedicalSys, cómo se clasifican y asignan los hallazgos, cómo se corrigen y cómo se verifica y cierra cada uno. Cualquier miembro del equipo debe poder repetir el ciclo siguiendo solo este documento.

## 2. Alcance

Aplica al repositorio `medicalsys-platform_v1` (13 microservicios y el gateway), a sus imágenes `medicalsys/*:local` y al gateway en ejecución. Implementa los lineamientos 6.1, 6.2 y 6.8 de la política PO-07.

## 3. Responsables

| Rol | Qué hace en este procedimiento |
|---|---|
| Responsable de Seguridad de la Información (RSI) | Ejecuta o encarga los escaneos, clasifica, asigna y aprueba el cierre. |
| Responsable de la corrección | Corrige el hallazgo asignado y entrega la evidencia. |
| Revisor de código | Aprueba el pull request de la corrección. |
| Propietario del sistema | Aprueba los riesgos aceptados. |

## 4. Requisitos previos

- Docker Desktop en ejecución. No hace falta instalar Trivy ni ZAP: se usan sus imágenes oficiales.
- Git Bash (Windows) o cualquier shell Bash.
- El repositorio clonado y un archivo `.env` creado a partir de `.env.example`.

Herramientas y versiones del ciclo de octubre de 2026:

| Herramienta | Versión | Uso |
|---|---|---|
| Trivy | 0.69.3 (`aquasec/trivy:0.69.3`) | Dependencias en `pom.xml` e imágenes de contenedor |
| OWASP ZAP | 2.17.0 (`ghcr.io/zaproxy/zaproxy:stable`) | Análisis dinámico pasivo del gateway |

## 5. Procedimiento

### 5.1 Preparar el entorno

1. Situarse en la rama que se va a escanear y anotar el commit.
2. Construir las imágenes y levantar la plataforma.
3. Comprobar que el gateway responde.

```
git rev-parse HEAD
docker compose up -d --build
docker compose ps
curl -s http://localhost:8080/actuator/health
```

Si no se dispone de la base de datos administrada, la plataforma se levanta con un MySQL desechable:

```
docker compose --env-file .env --env-file docs/seguridad/evidencias/evidencia.env -f compose.yaml -f docs/seguridad/evidencias/compose.evidencia.yaml up -d --build
```

### 5.2 Escanear

Un solo comando ejecuta las tres herramientas y deja los reportes fechados en `docs/seguridad/escaneos/<fase>/`. La fase es `antes` para la línea base y `despues` para el reescaneo.

```
bash docs/seguridad/escaneos/escanear.sh antes
```

El script ejecuta, en este orden, los siguientes comandos. Se listan para poder correrlos a mano.

Trivy sobre los `pom.xml` (un resultado por cada uno de los 14 manifiestos):

```
docker run --rm -v medicalsys-trivy-cache:/root/.cache -v "<repo>:/work:ro" -v "<salida>:/out" aquasec/trivy:0.69.3 fs --scanners vuln --severity HIGH,CRITICAL --format json --quiet --skip-dirs '**/target' --skip-dirs node_modules --output /out/trivy-fs-<fase>-<fecha>.json /work
```

Trivy sobre cada imagen. Se repite para las 14 imágenes que devuelve `docker image ls`:

```
docker image ls --format '{{.Repository}}:{{.Tag}}' | grep '^medicalsys/.*:local$'
docker save medicalsys/ms-gateway:local -o <tmp>/ms-gateway.tar
docker run --rm -v medicalsys-trivy-cache:/root/.cache -v "<tmp>:/images:ro" -v "<salida>:/out" aquasec/trivy:0.69.3 image --scanners vuln --severity HIGH,CRITICAL --format json --quiet --input /images/ms-gateway.tar --output /out/trivy-image-ms-gateway-<fase>-<fecha>.json
```

OWASP ZAP Baseline contra el gateway (araña de 1 minuto, escaneo pasivo con las reglas estables y beta, reportes HTML y JSON). ZAP deja en la misma carpeta el plan `zap.yaml` que ejecutó:

```
docker run --rm --user root -v "<salida>:/zap/wrk:rw" ghcr.io/zaproxy/zaproxy:stable zap-baseline.py -t http://host.docker.internal:8080/actuator/health -m 1 -J zap-baseline-<fase>-<fecha>.json -r zap-baseline-<fase>-<fecha>.html
```

Notas:

- En Docker Desktop el contenedor de ZAP llega al gateway por `http://host.docker.internal:8080`. `--network host` con `localhost` no funciona en Windows. Para otro destino: `ZAP_URL=http://host.docker.internal:8081 bash docs/seguridad/escaneos/escanear.sh antes`.
- `zap-baseline.py` termina con código 1 o 2 cuando encuentra alertas; es un resultado, no un error.
- Debe usarse `zap-baseline.py` y no `zap.sh -autorun zap.yaml`: solo el primero instala las reglas pasivas beta, entre ellas las dos que dieron hallazgos en la línea base. Con el segundo el escaneo termina sin alertas aunque existan.
- La primera ejecución de Trivy descarga unas bases de vulnerabilidades de alrededor de 3 GB; quedan en el volumen `medicalsys-trivy-cache`.
- Si existe una especificación OpenAPI se agrega el API scan de ZAP sobre ella. La plataforma no publica ninguna al 12/10/2026, por lo que no se ejecutó.
- Para escanear una rama distinta de la que está en el directorio de trabajo, se exporta a una carpeta temporal y se pasa como tercer argumento: `bash docs/seguridad/escaneos/escanear.sh antes develop-baseline <carpeta>`.

### 5.3 Clasificar y priorizar

1. Contar los hallazgos por severidad con el resumen del Anexo A.
2. Agrupar por componente y versión: muchas ocurrencias suelen deberse a una sola biblioteca repetida en varias imágenes.
3. Registrar por cada grupo: CVE, componente, versión instalada, versión corregida, severidad y CVSS.
4. Asignar el plazo según la tabla de la política PO-07:

| Severidad | CVSS | Plazo máximo |
|---|---|---|
| Crítica | 9.0 – 10.0 | 72 horas |
| Alta | 7.0 – 8.9 | 7 días |
| Media | 4.0 – 6.9 | 30 días |
| Baja | 0.1 – 3.9 | 90 días |

5. Ajustar la prioridad por contexto si corresponde (componente expuesto a Internet, datos clínicos, exploit público) y dejar escrita la razón.

### 5.4 Asignar responsables

1. Crear una incidencia en Linear por cada grupo de hallazgos, con la severidad, el plazo y el reporte de origen.
2. Asignarla al responsable del servicio afectado. Los hallazgos que tocan varios servicios (una biblioteca común) se asignan a una sola persona.
3. Publicar en la incidencia del escaneo el resumen por severidad.

### 5.5 Corregir

1. Trabajar en una rama por incidencia (`feature/sins-<n>`).
2. Dependencias: subir a la versión corregida más cercana en el `pom.xml`. Si la versión viene heredada de Spring Boot, se sobreescribe con la propiedad correspondiente (`tomcat.version`, `jackson-bom.version`, `bouncycastle.version`).
3. Paquetes del sistema operativo de la imagen: reconstruir con `docker compose build --pull`; el `Dockerfile` aplica las actualizaciones de seguridad.
4. Configuración: corregir el valor por defecto, no solo el del entorno local.
5. Ejecutar las pruebas del servicio y abrir un pull request que cite el hallazgo. Lo aprueba una persona distinta del autor.

```
cd services/<servicio>
./mvnw -B -ntp test
```

### 5.6 Reescanear

1. Con las correcciones integradas, reconstruir y levantar la plataforma como en 5.1.
2. Ejecutar el mismo script con la fase `despues`. No se cambian herramientas, versiones ni opciones.

```
docker compose up -d --build
bash docs/seguridad/escaneos/escanear.sh despues
```

3. Para las correcciones que un escáner no detecta (control de acceso, sesión, firma del webhook), capturar la evidencia funcional antes y después y la prueba general:

```
bash docs/seguridad/evidencias/capturar-evidencia.sh despues
bash docs/seguridad/evidencias/smoke-test.sh
```

### 5.7 Cerrar

1. Comparar los conteos de `antes` y `despues` y completar la tabla hallazgo → severidad → antes → después → pull request.
2. Un hallazgo se cierra solo si el reescaneo ya no lo reporta, o una prueba demuestra la mitigación, o existe un riesgo aceptado vigente según PO-07 6.8.
3. Los falsos positivos se cierran con la evidencia que lo demuestra.
4. Los hallazgos que siguen abiertos conservan su incidencia y su plazo.
